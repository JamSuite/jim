# Brainstorm: Group-level master spec (`000-current`)

*2026-06-30*

## The core idea

A formal, **group-level** spec — one per spec group (`foundation`, `storage`,
`dashboard`, …) — that is the **authoritative reference for the current state**
of everything inside that group's boundary.

- A **technical map / blueprint**: what the group does, and *how to build it*.
- **Current state only** — no history, no decision log, no "spec 028 changed X."
  Present-tense truth.
- Precise enough to build *to spec* and land close to the real thing.
- Numbered **`000-current`**: jim's work specs increment from `001`, so `000` is
  a natural slot for the master/living spec that sits before and above them.
  Sorts first; labels itself.

## The problem it addresses

- Numbered specs are **point-in-time**: accurate the day they're written, stale
  as later specs evolve the code.
- `ARCHITECTURE.md` is the only artifact the workflow keeps continuously updated
  — but it's **high-level** and deliberately **historical** (decisions, spec
  references, the "why" over time).
- So there's no single, current, build-grade map of a group. Illustrative
  thought experiment (explicitly **not** something jrko intends to run): delete
  the code, keep the docs, ask an agent to rebuild → you'd get a materially
  different product. The distance between "what the docs say" and "what would get
  rebuilt" is the gap this closes.

## The goal

1. **Maintain an accurate, evolving map** of each project.
2. Use the map(s) to **reason about high-level design** — application level *and*
   code level.
3. Use the map(s) to **generate verification contracts** that keep code and spec
   aligned and confirm the code does what's expected.

The `000-current` artifact is foundational; reasoning (2) and verification (3)
are its downstream consumers.

## Open threads (surfaced, not decided)

- **Altitude — what's on the page?** The value lives between *too high* ("it's
  just ARCHITECTURE.md again") and *too detailed* ("a redundant mirror of the
  code that stales as fast and costs as much to maintain"). What's in, what's
  deliberately out?
- **Authority direction.** Is `000-current` the *intent* code is verified against
  (spec wins; divergence = bug), or a *reflection* generated from the code (code
  wins; doc is derived)? "Build to spec" + "verification contract" leans toward
  spec-as-intent.
- **What keeps it current?** A workflow gate (any spec touching a group updates
  its `000-current`), a regen scan (à la `/jim:arch`), or a hybrid (curated
  intent + generated baseline, reconciled by the verification contract).
- **Relationship to `ARCHITECTURE.md`.** Per-group drill-down beneath the
  project-wide doc (arch = index, `000-current` = chapters), or does it absorb
  part of arch's role? How do the two avoid drifting from each other?
- **Cross-group contracts.** A boundary implies interfaces between groups. Where
  does the `storage`↔`dashboard` contract live — both maps, or a higher tier?
- **Bridge to the review pipeline (026–028).** `/jim:review` checks a build
  against its *point-in-time* spec today. "Verification contract" reads like the
  same machinery aimed at the *living* blueprint — possibly where (3) lives.

## Emerging model

**Altitude — direction.** Don't invent an altitude from scratch. *Amalgamate
the existing artifact templates* (spec / plan / research / security / review)
into one cohesive, present-tense, group-scoped view, and offer a **progressive
(layered) view** so each consumer pulls the depth it needs. Lean **toward
detail** — without becoming a second copy of the code.

- Unifying insight: amalgamation and the progressive view are the *same move*.
  The source artifacts already sit at different altitudes, so the layers fall
  out of them:
  - **Behavioral** (what + why) ← `spec.md`: responsibilities, contracts,
    user-facing functionality.
  - **Structural** (how) ← `plan.md` + `ARCHITECTURE.md`: components, key
    abstractions, build approach.
  - **Detail** (invariants) ← plan + code: data structures, invariants, key
    algorithms. This is the "lean toward detail" floor.
  - **Cross-cutting** ← `security.md`, reconciled against what actually
    shipped (`review.md`).

**Authority — resolved as a closed loop.** Intent leads (spec-as-intent), but
it is *not* static. Implementation can reveal the intent is impractical or
impossible as stated, so building feeds back:

- `000-current` is the authoritative **intent** you build *to*.
- The build → review loop produces **deltas**; the ones that only surface by
  building get **folded back** into `000-current`.
- Net: `000-current` is both the *input* to work and the *output* of it — the
  fixed point the pipeline converges toward. Code never becomes the authority;
  the *learnings* from building update the authoritative intent.

**Review's evolved role.** `/jim:review` becomes the loop's **sensor and
trigger**: it (a) verifies code against the living blueprint and (b) surfaces
what should be folded back. "Drift" stops meaning "drift from a point-in-time
spec" and starts meaning "divergence from living intent," with two resolutions:
*fix the code* (code drifted) or *fold the learning into `000-current`*
(building corrected the intent).

## New open threads

- **Fold-back mechanics.** *When* (a gate after review? inside it?), *who*
  (agent proposes + human approves, like every other jim gate?), and *how
  granular* (surgical section edit vs. regenerate the map)? Echoes the
  ARCHITECTURE.md discipline — keep it coherent, don't let ad-hoc edits stale
  it.
- **The detail floor.** How deep does the detail layer go before it's just code
  by another name? Maintenance cost concentrates in the deepest layer — every
  invariant written down is something the loop must keep honest.
- **Telling the two drift resolutions apart.** What's the signal that
  distinguishes "code is wrong, fix it" from "intent was wrong, fold it"? That
  judgment is the heart of the loop.

## Fold-back: stage & topology

**Leaning: a stage *after* review, not inside it.** Review's lens is *recent
diff vs. the numbered spec* (verification of a unit of work — narrow,
point-in-time). Fold-back's lens is *whole group vs. the living blueprint*
(integration — broad, present-tense). Different lenses → different context.

- Pros of after-review (B): right context (loads `000-current` + the
  whole-group view fresh, catches *non-local* map implications a local diff
  has); keeps review crisp; decoupled cadence (batch several reviewed specs
  into one fold-back when the dust settles).
- Cons of B: another stage/gate; the blueprint *lags* if fold-back is skipped.
- Pros of inside-review (A): reuses the loaded diff context (cheaper); drift
  findings are right there.
- Cons of A: diff-scoped context biases edits toward where the diff touched;
  conflates "verify the unit of work" with "maintain the master map."

**Resolution that grabs both:** B *consumes review's verdict ledger* (spec 028)
as structured input — no re-deriving the diff analysis (A's efficiency), but
running with the whole-group lens (B's correctness). The ledger is the
hand-off; artifacts bridge the stages, not shared context — already how jim
works.

**Tracked obligation, not optional.** To keep the "stays current" promise,
fold-back is a real gate or a visible staleness flag ("`000-current` is behind
N reviewed specs"). Batching is fine; *forgetting* is not.

**Topology — swarm *and* broad, split by sub-task:**
- *Detection* (where does code diverge from the blueprint?) → adversarial
  **swarm**, each agent owning a region / layer / invariant. Coverage + diverse
  lenses + parallel; the 027 investigator pattern reused. This *is* the
  verification job (goal 3).
- *Integration* (rewrite the blueprint to absorb the learning) → single
  **broad-view synthesizer**; coherence needs one context holding the whole
  map. A swarm can't co-author one consistent document.
- So: **swarm-detect → synthesize-fold → human approve.**

## The invariant floor

**The blueprint captures the invariant set; it omits the non-load-bearing
implementation the invariants don't pin down.** If something is invariable — a
decision / requirement / constraint / contract / blocker — it belongs in the
blueprint. What's omitted is the *variable* realization: the implementation a
conforming engineer (or agent) is free to choose.

**Amendment — invariant ≠ altitude.** Code itself can be an invariant (e.g.
"all interfaces must have this shape," "repository methods take a context
first," "errors are values"). So invariant-vs-variable is *orthogonal* to the
behavioral / structural / code axis — an invariant can live at any altitude,
code-level shape and contract rules included. The floor is **jagged**: it
reaches down into the code wherever the code's *form* is load-bearing, and stops
wherever the form is a free choice. "Code is the variable part" was too clean —
code *constraints* are in; code *choices* are out.

- **Altitude rule, restated:** be exhaustive about *constraints* at every level,
  not about *implementation instances*. Still no "second copy of the code" — you
  capture the *rule* ("interfaces have this shape"), never the *instances* (each
  interface's body).
- **Convergence with goal (3), now richer:** invariants *are* the verification
  contract ("assert these hold"). Admitting code-level invariants gives the
  contract a spectrum — behavioral assertions (hard; tests / judges) through
  structural / code-shape assertions (cheap; lint / type / AST / grep). The
  swarm checks the whole spectrum.
- **Cost bound still holds:** you capture the *rule* (low-churn), not the
  *instances* (high-churn). Code-shape invariants are standing rules — they
  don't reintroduce per-diff churn.
- **Tightens the rebuild experiment:** a rebuild must satisfy the behavioral
  *and* the code-shape invariants → not just functionally equivalent but
  structurally conformant. The more code-shape invariants captured, the closer
  the rebuild's *form*, not just its behavior.

## What makes a constraint load-bearing

**A union of independent sources — not one adjudicator.** A constraint earns a
place in the blueprint if *any* of these hold:

- **Author intent** — someone *decided* it (a deliberate design choice).
  Provenance: a spec / plan / declaration. *Declared, top-down.*
- **Cross-boundary usage** — something outside the boundary *depends* on it.
  Provenance: the actual dependency graph. *Discovered, bottom-up.*
- **Verification dependency** — a contract would *break* if it changed.
  Provenance: the contract set itself.

So the blueprint fills from both directions at once: declared intent (down) and
discovered dependencies (up). The fold-back loop is how the bottom-up ones get
surfaced and promoted to explicit invariants.

**The sources' *disagreement* is a diagnostic (serves goal 2).** Agreement → a
solid invariant. Divergence → a flag for a human:

- Intent says contract, nothing uses it → dead / speculative (drop?).
- Usage depends on it, never declared intent → emergent contract: promote it,
  or it's a *boundary leak* to sever.
- Verification asserts it, no intent and no usage back it → stale / over-fit
  test.

This turns the alignment swarm into more than a checker — it's a design-smell
detector, and it gives the loop a *retirement* direction: "stale" isn't only
"code violated it," it's also "no source justifies it anymore."

## Cross-group contracts

Where does the `storage`↔`dashboard` contract live, and how does it stay
coherent across both maps?

**Not a new primitive — the boundary case of the load-bearing-source model.** An
inter-group contract is an invariant whose sources straddle a boundary:
- the **provider** *declares* the surface (author intent, top-down),
- the **consumer** *depends* on it (cross-boundary usage, bottom-up).

So the same disagreement-diagnostic polices it:
- consumer depends on something the provider never declared → **boundary leak**
  (promote to the surface, or sever),
- provider declares surface nobody uses → **dead surface** (trim),
- both agree → solid contract.

**The contract = the public projection of a group's invariants.** Each
`000-current` splits its invariant set into *internal* (private, load-bearing
within the group) and *boundary* (the exposed surface others may depend on).
Groups depend on each other's exposed surface, never internals — and the leak
detector *is* what enforces that encapsulation.

**Where it physically lives — content vs. graph:**
- *Content* (what `storage` exposes + its guarantees) → the **provider's
  `000-current`**, single source of truth. Consumers *reference* it (a
  dependency edge); they don't re-declare it → no dual-source drift.
- *Graph* (who depends on whom — the inter-group edges) → a **higher tier**.
  Plausibly the ARCHITECTURE.md job: per-group maps = content; project doc =
  the composition/index. (Starts answering the arch-split thread.)

**Payoff — pre-build blast radius.** Because the graph is explicit, the
blueprint knows the blast radius of a change *before* you build: touching an
*internal* invariant → consumers unaffected; touching a *boundary* invariant →
flag every dependent group. A breaking-change detector that reads the map, not
the diff.

**Open fork — authority at the boundary** (same shape as the global one, scoped
down):
- *Provider-declared*: provider owns its surface; consumers adapt. Clean
  ownership; provider can't see who'd break.
- *Consumer-driven* (Pact-style): the union of consumer needs defines what the
  provider must keep. Stronger safety, more coupling.
- *Hybrid*: provider declares the surface (down); consumer expectations are
  discovered and feed the verification contract (up) — maps cleanly onto the
  both-directions fill.

## Hybrid boundary: the two-faced map

Authority at the boundary = **hybrid** (chosen). That gives each map a concrete
shape: every `000-current` grows two faces —
- **provides** — the surface this group declares (author intent; hand-written,
  small, low-churn),
- **requires** — what it actually depends on from others (discovered from
  usage; machine-extracted, not hand-authored).

**The contract is owned by neither map — it's the reconciliation of
`A.requires ↔ B.provides`.** (Refines the earlier "provider owns the contract
text": the provider owns its *provides* side, the consumer owns its *requires*
side; the contract is the checked relation between them.) This flips drift into
a feature: drift becomes a *failed reconciliation* — the detector firing, not
silent divergence. The mismatches name themselves:
- requires something B never declared → **leak** (reaching past the surface),
- requires something B *removed* → **breaking change** (regression vs. a live
  consumer),
- B provides what nobody requires → **dead surface** (trim).

**Honors the cost line.** Only `provides` is hand-written (intentional,
low-churn); `requires` is discovered, so the expensive half maintains itself.
Granularity recurses to the detail floor: `requires` records *which of the
provider's declared guarantees* a consumer leans on ("relies on
read-after-write"), not every call site.

**Settles the arch-split for free.** Per-group maps hold the two faces
(content); the project doc holds the **graph** — the join where everyone's
`requires` edges meet everyone's `provides`. Content low, composition high, and
they can't contradict because the graph is *derived* from the faces, not a
third hand-maintained copy.

## Verification contracts: fixed floor, tunable ceiling

Per-group and **context-dependent** — groups differ in context and boundaries,
so verification differs. Shape: a fixed floor + a tunable ceiling, climbed
per-invariant.

- **Floor — always on, free.** If a cheap mechanical check exists for an
  invariant (lint / type / AST / grep), it runs. No knob; never skip free.
- **Ceiling — escalates to any available means, gated by appetite.** Property
  tests, judges, adversarial swarms. The blueprint is the highest-value
  artifact, so paying for depth is justified — but the user sets the dial.

**The invariant's type picks the rung.** Code-shape invariants fall to the
cheap floor; behavioral invariants need the expensive ceiling. So
"context-dependent per group" falls out for free: different invariant sets →
different verification mixes, no global policy to fight.

**Split method from appetite:**
- *Method* is intrinsic to the invariant ("code-shape → AST-checked") → lives
  in `000-current` beside the claim. The blueprint then states not just *what's
  true* but *how you know it* — claim + proof-method, the "highest quality" bar.
- *Appetite* is the user's dial → lives in config (jimconf).

**Make the knob criticality, not a raw cost slider.** Reuse jim's priority
vocabulary (critical / high / medium / low) for invariants: a `critical`
boundary invariant climbs the full ladder; a `low` one gets cheap-or-nothing.
The dial = "at what criticality does expensive verification kick in" — global
default, per-group override (spend hard on `auth`, lightly on `dashboard`).

## Fold-back trigger: a standard gate

The fold-back is a **gate with the same shape as the rest of the jim pipeline**:
- **Default: human approval.** Upholds jim's human-in-the-loop principle — the
  blueprint (the highest-value artifact) doesn't change without your eyes.
- **`auto_` config knob** enables a hands-off feedback loop for users who've
  built the trust (mirrors `auto_security` and friends). The *default* honors
  the "not hands-off vibe coding" non-goal; the knob is a deliberate,
  user-owned override.

**What you approve is concrete:** a proposed *diff* against `000-current` — the
verdict ledger (028) as evidence, plus the synthesized delta. Reviewable like a
PR; no re-derivation. (Agent proposes, human approves — jim-idiomatic.)

**Natural refinement — grade auto by the same criticality dial.** Auto-mode
needn't be all-or-nothing: auto-fold low/medium invariant changes, but always
require a human for *critical / boundary* changes (high blast radius — they
ripple to dependents via the contract graph). One criticality concept then
drives both verification appetite *and* fold-back autonomy.

## Surfaced (out of scope → filed as an issue)

**The spec group becomes load-bearing.** This whole model promotes the group
from a convenient label to the **context boundary** — intent + code under one
umbrella, the loosely-coupled module / bounded context, now carrying
provides/requires faces, verification contracts, and external consumers. That's
a dramatic shift from today's ad-hoc group naming (pick a name that fits the
spec). Choosing a group *becomes* drawing a module boundary.

*How groups come to be well-formed* — choosing boundaries and naming relations
deliberately — is **upstream** of this brainstorm (which designs the artifact
and assumes well-formed groups). A prerequisite, not just a follow-on: bad seams
propagate into the blueprint, contracts, and verification. Filed as issue #19
(`20260630-build-intelligence-for-context-aware-spec-group-definition`) for
separate research/spec.
