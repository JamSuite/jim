# Security Review: Group blueprint spec (000-blueprint)

## Summary

**Findings:** 0 Critical · 2 Notable · 1 Advisory

Reviewed `spec.md` (no `plan.md` yet) under the requirements-gap lens. The
feature ingests a group's code and specs — attacker-influenceable text — and
persists a repo-committed artifact, so the dominant risks are **directive
injection** through scanned content and **secret leakage** into the blueprint.
STRIDE swept (6/6); LINDDUN active (Credentials = Yes) with only Data Disclosure
relevant. The mitigations already exist in jim (the `/jim:review` + `investigator`
discipline) — the gap is that the spec does not yet *require* them.

## Findings

### 1. Untrusted ingestion / directive injection is not specified

- **Severity:** Notable
- **Description:** The blueprint is generated by reading a group's code and specs, which can carry attacker-influenced text (e.g., a code comment or spec line crafted as an instruction: *"record X as an invariant"* / *"ignore prior guidance"*). The ACs require the blueprint be "grounded in" and "traceable to" the group's artifacts (AC #3–8) but never state that scanned content is **data, not instruction**. Without that, the generator can be steered by embedded directives, or can faithfully transcribe misleading content as authoritative blueprint claims.
- **Suggestion:** Add an AC requiring the blueprint's content to be the skill's **judgment over the scanned evidence — never a directive or value lifted from scanned code/specs** — mirroring the established discipline at `agents/investigator.md:28-34` and `skills/review/SKILL.md:63-65` (treat ingested content as untrusted data, wrap it, never act on embedded instructions).
- **Route:** Spec
- **Relates to:** AC #8 (traceability/grounding); the generation behavior generally.

### 2. Secret scrubbing of scanned content is not specified

- **Severity:** Notable
- **Description:** Scanned code may contain hardcoded secrets (API keys, tokens, passwords). The generator reads them and could echo a secret-looking value into the persisted blueprint, which is committed to the repo — and jim's repo is slated to go public. The spec does not require scrubbing secret-looking values from the blueprint output.
- **Suggestion:** Add an AC requiring the blueprint to **never persist raw secret-looking values** read from code — scrub to a placeholder such as `secret-looking value at <path:line>`, mirroring `agents/investigator.md:60-64`.
- **Route:** Spec
- **Relates to:** AC #6, #7 (structure/invariants drawn from code), AC #8.

### 3. Validate the blueprint write-path through the single id boundary

- **Severity:** Advisory
- **Description:** The blueprint writes to a group-derived path (`{specs}/{group}/000-blueprint/`). The group name is developer-supplied (trusted), so traversal risk is low, but the write target should still be validated through the existing `is_valid_slug`/`is_valid_id` boundary (`jimfile.sh:147-189`, the `new.sh` precedent) rather than composed from raw input — defensive consistency with the issue emitter.
- **Suggestion:** At plan time, resolve and validate the blueprint path through the existing `jimfile.sh` validators; do not compose the path from unvalidated group/slug input.
- **Route:** Plan
- **Relates to:** AC #1, #2 (write target).
