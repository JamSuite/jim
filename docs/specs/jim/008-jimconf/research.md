## Local Patterns

- **Skill structure:** every SKILL.md uses YAML frontmatter (`name`, `description`, `agent`, `argument-hint`) + markdown body. Template references are uniformly `assets/<name>-template.md` relative to the skill.
- **Path-construction patterns:** dynamic paths like `docs/specs/{group}/{id}-{name}/{spec|plan|research}.md` and `docs/debug/{YYYYMMDD}-{topic}.md` appear as variable interpolation in skill prompts (e.g., `skills/spec/SKILL.md:127`). The LLM is currently responsible for assembling these strings at runtime.
- **Existence-check pattern (the duplication the spec aims to eliminate):** prose like *"if it exists"*, *"Check for existing"*, *"if X is missing"* appears across **7 skills in 20+ separate occurrences** (e.g., `skills/spec/SKILL.md:32`, `skills/vision/SKILL.md:26`, `skills/research/SKILL.md:92`). Each is interpreted by the LLM, not deterministically resolved.
- **No executable code anywhere.** ARCHITECTURE.md L181, L183 explicitly: *"pure markdown — no build step, no dependencies, no package manager."* Verified by `find` for `*.py`/`*.sh`/`*.js`/manifest files — zero matches.
- **Test framework:** none exists. **No `tests/`, no `*.test.*`, no `bats`, nothing.** This spec creates jim's first need for automated tests *if* scripts are adopted.

## Security & Performance

- **Never `source` user-supplied config files.** Sourcing executes the file as bash; a malicious `jimconf.toml` could run arbitrary commands. Always parse with `grep`/`cut`/`sed`, never with `source` or `eval`.
- **`allowed-tools` is documented but enforcement is buggy** (open Anthropic issues #14956, #18837, #37683). Treat `allowed-tools` declarations as documentation, not security.
- **`!`-injection runs every skill invocation.** Negligible at human-typing scale; no caching needed.
- **`${CLAUDE_SKILL_DIR}` is per-skill, not plugin-wide.** Sharing one resolver across jim's 11 skills requires either (a) referencing a sibling skill's script via `${CLAUDE_SKILL_DIR}/../conf/scripts/jimconf.sh` (works, but coupled to layout) or (b) copying the script into each skill (duplication). Architect's call.
- **Failure mode if config file is malformed:** the `grep`/`cut` parse pattern silently returns empty for missing or malformed keys — falls through to defaults, which matches the spec's "no strict mode" decision. Acceptable.

## Recommendations

Decisions belong to the architect; this section presents options with trade-offs.

### Recommended path

**File:** `jimconf.toml` at project root (visible, single canonical location).

- Visible file; mirrors `package.json`, `Cargo.toml`, `tsconfig.json`.
- Cross-agent-neutral — not under `.claude/` or any agent's dotdir.
- The user explicitly ruled out a `.jim/` directory ("the whole point is to make where we store documents more flexible") and ruled out `docs/jim/jimconf.toml` (circular — `docs/` itself is configurable).
- One canonical location. Multi-location lookup is deferred to a future `/jim:file` skill (already out-of-scope per spec 007); that's where directory-walk semantics belong.

**Format:** flat `KEY = "value"` lines.

```toml
specs_path = "docs/specs"
architecture_path = "ARCHITECTURE.md"
vision_path = "VISION.md"
roadmap_path = "ROADMAP.md"
brainstorms_path = "docs/brainstorms"
debug_path = "docs/debug"
```

This is **valid TOML** (a real TOML parser will accept it) **and** trivially bash-parseable with `grep | cut | tr` — no `source`, no `jq`/`yq`/`stoml` dependency. Editors detect `.toml` for syntax highlighting. A future Python/Node port reads the same file with a real TOML parser. Best of both worlds.

### Resolution mechanism — three options for the architect

**Option A — Pure-markdown, `!`-injection in each skill.**

```yaml
allowed-tools: Bash(grep *) Bash(cut *) Bash(echo *) Bash(test *)
---
Architecture path:
!`grep '^architecture_path' jimconf.toml 2>/dev/null | cut -d= -f2- | tr -d ' "' || echo ARCHITECTURE.md`
```

*Pros:* No new code. ARCHITECTURE.md "pure markdown" claim survives. Zero deps.
*Cons:* Resolution prose duplicated in every skill (still better than current existence-check prose, but not eliminated).

**Option B — Single resolver script, multiple consumer skills.**

Add `skills/conf/scripts/jimconf.sh` (or `.py`). Skills invoke via:
```
!`bash ${CLAUDE_SKILL_DIR}/../conf/scripts/jimconf.sh get architecture_path`
```

*Pros:* Single source of truth. Replaces 20+ existence-check prose patterns with one tested codepath. Format-agnostic — script can swap parser later. Foundation for the prompt-refactor follow-on hinted at in the spec.
*Cons:* First executable code in jim — **ARCHITECTURE.md must be updated** in the same PR set. Cross-skill `${CLAUDE_SKILL_DIR}/..` reference is conventional but coupled to layout. Needs tests.

**Option C — `/jim:conf` as user-facing skill only; other skills inline (Option A).**

*Pros:* Avoids cross-skill coupling.
*Cons:* Logic duplication — exactly what the spec's Open Question #3 was trying to eliminate. **Not recommended.**

**My read:** Option B is the strongest if the architect is willing to amend ARCHITECTURE.md's "pure markdown" claim. Option A is the safer minimum-change choice if pure-markdown is sacred. Either is acceptable for v1; the differentiator is appetite for executable code.

### Testing strategy (only if Option B chosen)

- **bats-core** for bash, `pytest` for Python — both well-supported. **bats-core wins on minimum-deps if bash chosen.**
- Tests live in `tests/` at repo root, excluded from distribution via `.gitattributes export-ignore`. Don't colocate tests inside production scripts.
- If Option A wins, no test harness is needed; the AC #8 verification is a documented walkthrough against a non-default layout.
